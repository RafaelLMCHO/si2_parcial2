1. OBJETIVO
--------------------------------------------------------------------------------
Migrar unicamente la persistencia de las VENTAS OFFLINE web (CU-28) de
localStorage a IndexedDB, manteniendo intactos reservas (CU-26), cambios (CU-29),
catalogo, soft-locks e inventario.

Tambien corregir el mensaje enganoso del stub de POS (solo texto, sin wiring).


2. DECISIONES APROBADAS
--------------------------------------------------------------------------------
[1] DB nueva: FashionStoreVentasOfflineDB (NO reutilizar FashionStoreOfflineDB).
[2] Tras migrar ventas legacy a IndexedDB, eliminarlas de
    localStorage['cola_operaciones_offline'].
[3] OfflineQueueService.hasPending() debe considerar las ventas en IndexedDB.
[4] pos.service.ts: solo corregir el texto del log. NO conectar al CU-28 real.
[5] Tests con fake-indexeddb (devDependency).

Supuestos:
- Las ventas en estado 'confirmada' / 'en_conflicto' se conservan en IndexedDB
  (igual que hoy se conservan en localStorage); hasPending las ignora.
- Sin sincronizacion entre pestanas.
- Fallback a localStorage solo si indexedDB no existe (modo privado / SSR).

4. ARQUITECTURA
--------------------------------------------------------------------------------
- Espejo en memoria (Angular signal) como fuente de verdad en la sesion.
- Write-through asincrono serializado hacia IndexedDB.
- Hidratacion al arranque (provideAppInitializer) leyendo IndexedDB.
- Las APIs publicas de CU-28 / CU-30 / CU-31 se mantienen sincronas/Observable.
- Creacion perezosa de la DB: solo se abre/crea en el primer enqueue o en
  hydrate() si existe marcador o ventas legacy.

Flujo:
  CU-28 registrarVenta()
    -> ventasStore.enqueue(record)
    -> mirror.push(record)  (sincrono)
    -> persistChain = persistChain.then(put en IDB)
    -> offlineQueue.refreshStatus()

  App (al volver online)
    -> auth.pendingOffline() == true
    -> CU-31 sincronizarLote()
    -> pendientes = cola localStorage SIN ventas + ventasStore.listPendientes()
    -> POST /api/v1/sync
    -> confirmadas/conflictos a cada fuente


5. NUEVO SERVICIO
--------------------------------------------------------------------------------
Archivo: frontend/src/app/core/ventas-offline-store.service.ts

constantes:
  DB_NAME    = 'FashionStoreVentasOfflineDB'
  DB_VERSION = 1
  STORE      = 'ventas_offline'
  MARKER_KEY = 'fashionstore_ventas_idb_initialized'
  FALLBACK_KEY = 'fashionstore_ventas_offline'

interface VentaOfflineRecord {
  id: string;                  // uuid local (igual al usado hoy en CU-28)
  tipo: 'venta_offline';
  sucursal_id: string;
  payload: Record<string, unknown>;
  creada_en: string;
  idempotency_key: string;     // 'VENTA-OFF-' + uuid (formato actual)
  estado: 'pendiente' | 'enviada' | 'confirmada' | 'en_conflicto';
  intentos: number;
  ultimo_error?: string;
}

Estado interno:
  private readonly itemsSignal = signal<VentaOfflineRecord[]>([]);
  readonly items = this.itemsSignal.asReadonly();
  private persistChain: Promise<void> = Promise.resolve();
  private dbPromise: Promise<IDBDatabase> | null = null;
  private fallback = false;
  private hydrated = false;

API publica:
  hydrate(): Promise<void>
  list(): VentaOfflineRecord[]
  listPendientes(): VentaOfflineRecord[]
  hasPending(): boolean
  enqueue(record: VentaOfflineRecord): void
  markEnviadas(ids: string[]): void
  applySyncResult(confirmados: string[], conflictos: {id:string; detalle?:string; causa?:string}[]): void
  revertEnviadas(): void
  remove(id: string): void
  whenIdle(): Promise<void>

Comportamiento:

hydrate()
  - nunca lanza; try/catch interno con console.warn.
  - si typeof indexedDB === 'undefined':
      fallback = true; leer FALLBACK_KEY; setear items; hydrated = true; return.
  - si no existe MARKER_KEY:
      leer localStorage['cola_operaciones_offline'].
      extraer registros con tipo === 'venta_offline'.
      si no hay ventas legacy: hydrated = true; return SIN abrir la DB (lazy).
      si hay:
        (a) abrir DB y put() de cada venta (dedupe por id).
        (b) SOLO si (a) tuvo exito, reescribir la cola localStorage sin ventas.
        (c) setear MARKER_KEY = '1'.
  - si existe MARKER_KEY: abrir DB y leer todo el store.
  - cargar itemsSignal con lo leido; hydrated = true.

openDb()
  - indexedDB.open(DB_NAME, 1).
  - onupgradeneeded: createObjectStore(STORE, { keyPath: 'id' });
    store.createIndex('estado', 'estado', { unique: false }).
  - resolver/rechazar correctamente.

enqueue(record)
  - itemsSignal.update(v => [...v, record]).
  - escribir via persistChain:
      si fallback: guardar items en FALLBACK_KEY.
      si no: abrir DB (lazy) y put(record).
  - navigator.storage?.persist?.().catch(() => undefined) best-effort.
  - errores de cuota: console.warn y conservar el espejo (no romper la venta).

markEnviadas(ids)
  - actualizar espejo a 'enviada'; persistir esos ids.

applySyncResult(...)
  - confirmados -> estado 'confirmada' (eliminar ultimo_error).
  - conflictos  -> estado 'en_conflicto' + ultimo_error con detalle/causa.
  - persistir.

revertEnviadas()
  - los 'enviada' vuelven a 'pendiente'; persistir.

hasPending()
  - return itemsSignal().some(v => v.estado !== 'confirmada')
  - NO debe tocar IndexedDB (debe ser sincrono y barato).

whenIdle()
  - return this.persistChain.

IMPORTANTE: este servicio NO debe inyectar OfflineQueueService (evita ciclo).
Los llamadores hacen offlineQueue.refreshStatus().
